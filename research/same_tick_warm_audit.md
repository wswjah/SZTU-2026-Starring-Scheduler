# 同 tick 镜像预热：独立审计和自主消融

日期：2026-11-15。此实验从正式 85 分源码 `versions/v3_aggressive/main.cpp` 独立加入一处发令变换，借鉴的是公开题目允许的操作组合。未替换为同学程序，未使用 V4 风险树，未改变普通调度的选机、工作流接纳和冷启动计划；仅在原策略已经选好机器后判断是否预热。根目录 85 分文件与冻结 V4 文件均保持原指纹。

## 题面依据和适用条件

依据 `reference/problem.md` 4.1–4.3、6 节：

1. RUN 时即处理所有镜像层并写入缓存，而非等准备期结束才写入。
2. KILL 仅要求该作业正在运行；终止后作业回到待运行状态，已拉取层保留。题面没有“同 tick 禁止再次 RUN”或“本 tick 一个作业只允许一条指令”的限制。
3. 运行费为 `c * p_d * (r-s)`。RUN 和 KILL 在同一 tick，第一轮运行费为 0；传输费、仓库拉取费已经产生，不退款。
4. 再次 RUN 会重新处理每份输入。因此非本机架输入的网络费、网络时延都不能省略。镜像数据保留不等于输入数据也保留。
5. 每 tick 最多 20,000 条指令。一次预热需要两条额外指令，必须留足三条 RUN/KILL/RUN 的空间。

`tpj.cc` 只写明不提供评测源码，无法给出 judge 源码级证明。下述实际合法性、对账和利润均由原始 `tpj_win.exe` 闭环运行验证；没有反编译或修改评测机。

设原机器的镜像准备时间为 `P`，输入传输时间为 `X`，本轮网络费为 `F`，仓库拉取费为 `Q`，CPU 每 tick 费用为 `C`。普通运行的准备时间为 `S=max(P,X)`，立即费为 `F+Q`。若镜像能完整保留，则同 tick 预热后：

- 首 RUN 仍支付 `F+Q`，同 tick KILL 的运行费为 0。
- 再 RUN 支付 `F`，无镜像拉取，准备时间为 `X`。
- 相同真实计算时长下，费用差为 `F-C*(S-X)`，完工至少提前 `S-X`。

本候选采用充分且保守的条件：镜像所有层大小之和不超过目标机器缓存容量；`S>X`；`F<=C*(S-X)`；剩余指令数不少于 3。只要一项不满足，就按原策略正常 RUN。

这里不要求镜像适合机架缓存：第一轮后只要完整保留在机器缓存，第二轮全是机器命中即可。相反，单层超过机器容量，或多层总量超过容量时，重启仍可能重拉甚至逐层反复淘汰；本候选一律不尝试。总大小按原镜像序列求和，重复层也计入，因此容量检查可能偏保守，但不会因去重失误放宽条件。零字节非本地输入仍保留网络距离时延。

## 状态和账本审计

实现位于 `candidates/v5_same_tick_warm.cpp` 1570 行附近。两次真实 RUN 的缓存访问各执行一次 `pull_image_layers`，第二轮同时断言仓库和机架拉取量均为 0。实际测试使用未定义 NDEBUG 的程序，断言处于开启状态。

第一轮仅在发令前按原费用增加一次账本，再在同 tick 撤销运行费率和配额占用；立即费用保留。原始仿射账本 `offset + rate*tick` 因此与 RUN/KILL 顺序一致。第一轮对 CPU、内存、DAG 运行前驱位、就绪队列的净效果都是 0，代码只保留最终第二轮的运行状态，不经过普通 FAIL/KILL 处理入口。这避免把即时终止当成真实时长样本。

第二轮的 `job.start_tick` 仍是当前 tick，`job.prepare_time` 精确写为输入传输时长 `X`，实际立即费为第二次网络费 `F`。完成后的租户时长学习仍用 `finish-start-prepare`，不会把省去的镜像等待误当计算时长偏差。真实后继输出仍按实际完成机器机架发送。

第一轮 RUN 必须已经满足普通 RUN 的配额、CPU、内存和前驱要求；它同 tick 释放后第二轮可以使用同样资源。两条指令之间没有事件、QUOTA、UNDO 或 FAIL 插入。后续真实 FAIL 仍按原规则释放最终运行的作业并清故障机器缓存；以后重启也重新检查是否适合预热。UNDO 只撤销管理员配额修改，不回滚缓存或已发生费用。

镜像和前驱状态都只使用当前可见状态，无未来事件、隐藏真实时长、世界 ID 或种子特征。提前完工会改变后续缓存、竞争和接纳，所以上述单次费用改进并不构成整个世界利润必增的数学保证；必须闭环验证。
