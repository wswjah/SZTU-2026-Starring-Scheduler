## 最大差异：同 tick 先预热，再真正运行

实际实现见阅读版 `main.cpp:470–496`：对每个候选机器同时估价普通启动和预热启动；当预热更便宜且机器现在即可运行时，依次调用 `runJob`、输出 `KILL`、`release`，再调用 `runJob`。三个命令处于同一个 tick。

这用到了三条协议的组合：RUN 当场把镜像层写入缓存；KILL 保留已拉取的层；运行费按释放 tick 减启动 tick 计。第一次 RUN 的运行费因此为零；如果镜像层能留在机器缓存中，第二次 RUN 就不用等待拉取。真实执行不会跳过传输、仓库费或配额检查：`runJob`（234–259 行）每次重新计算输入传输、缓存、准备时间、立即费用和资源占用，`release`（197–212 行）释放资源并结清实际运行费。

准确地说，它节省的是准备期时间及该期间占用 CPU 的费用，不是免掉第一次仓库拉取费。外部/前驱输入的网络费会支付两遍，镜像大于缓存时也未必能消除第二次拉取。选机估价式明确加入第二遍传输费（473 行）。

作者报告这项改动单独带来约 +17.5% 本地总利润，最终 v2 相对其 v1 +23.6%；这是作者消融数据，尚不能认定就是本项目从 85 到 96 的贡献。我们此前只有常规 RUN 放置，没有这条命令序列；主要在估价、拒绝风险和尾任务救急上优化，因而没有改变每次冷启动的物理等待成本。这是当前最值得首先做独立闭环实验的差别。

这里没有读出隐藏真实时长、没有窥探未来事件，也没有把 KILL 当作完整时长标签；它属于命令执行时序带来的缓存效果。它与输入中的配额 `UNDO` 无关。

## 覆盖范围和可移植性

当前 V4 的 `schedule:1752–1754` 明确跳过单流程超过 40 个作业的情况，规划数组也固定为 40。官方题面没有公开单流程 ≤40 的保证。对方 `flowEstimate` 使用 65,536 长度的每流程临时数组，未见这条 40 限制。因此大 DAG 是另一项覆盖差异；目前没有正式失败详情，不能断言失分由此造成。

也不能把对方代码未经审查整体换入：例如其后继看一步数组是固定 `qr[8][5]`（413 行），对超过 8 个后继的循环边界需要另外核验；缓存价格预览按当前 membership 求和，没有逐层模拟超容量层引起的淘汰；我方真实账本使用更宽整数。作者已通过的场景不能替代对公开完整范围的检查。

优先顺序建议：先测同 tick 预热的独立作用，同时保留无预热对照；随后分开试五情景/终局容差和忙机器预约，最后再考虑扩大机架候选与改变时长学习。不要一次混入所有差异，便于判断实际收益和回退来源。
