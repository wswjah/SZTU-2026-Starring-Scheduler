## 逻辑与实现

原优先级分母中的工作量主要为剩余 CPU 核时，同样核时但高内存的流程可能占据更多机器资源，理论上应有更高的机会成本。本轮只做两个结构版本，没有继续枚举系数。

新增每条流程的 `estimated_memory_work`、`unfinished_memory` 和运行中估计完成的内存时长。它们在 WF 累加、DONE 减去对应作业；FAIL/KILL 后作业仍待重跑，不错误扣除未完成工作。每 tick 与原 CPU 进度同样扣除运行中已估计完成的部分。新增每机架在线总内存、空闲总内存和空闲 CPU 汇总，不改变真实账本、资源检查或可行性。

令 `C` 为原剩余 CPU 核时，`M` 为剩余内存时长；`Ccap=min(租户到根的最小总配额,首选机架在线总CPU)`，`Mcap` 为该机架在线总内存。

1. `dominant`：优先级工作量改为 `max(C, M*Ccap/Mcap)`，相当于取 CPU 与内存两种归一服务时间中的较大值，再换回 CPU 核时单位。
2. `pressure`：工作量改为 `max(C, M*(Ccap+Cfree)/(Mcap+Mfree))`。其中 `Cfree` 同时受当前配额余量和机架空闲 CPU 限制。容量加空闲量使实际紧张程度参与价格，同时避免当前某资源几乎满载时价格无界。

只替换最终 priority 分母中的 `.8*work`；原配额排队、费用估计、收益估计、紧急度与进度加成均不变。

预测风险包括：CPU/配额本来已占主导导致内存项很少触发；机架总内存不能精确描述单机碎片；提高内存机会成本可能错误压低高利润内存型流程的优先级。

## 实现是否生效

使用同一源文件的 `V4_RESOURCE_STATS` 调试宏，在三个训练场景抽检最终排序时内存项真正大于 CPU 项的比例。调试与正常版本的完整评测 report 字符串逐例一致。

| 场景 | dominant 触发比例 | pressure 触发比例 |
| --- | ---: | ---: |
| fast_00 | 1.05% | 0.65% |
| heavy_00 | 2.14% | 1.78% |
| standard_00 | 1.04% | 0.26% |

这说明逻辑并未失效；在抽检场景中，CPU 和租户配额确实多数时间主导归一资源工作量，与大量利润完全不变的现象相符。不能由三个抽检场景推断所有正式数据的瓶颈。
