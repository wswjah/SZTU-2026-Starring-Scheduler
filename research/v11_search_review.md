# V11 更昂贵的放置搜索

基于冻结v10_input_fix（正式99分策略及8MiB输入token修复），在看结果前固定3个变体。只使用train16，范围内14例和2个large日志边界例分别汇总；没有新增提交或读取V11新场景。

full_racks：RK从16提升到30，枚举全部机架；warm_rank：仍保留16架，但用该架在线且可容纳目标需求机器的最少仓库缺层费排序，避免架缓存冷、机器缓存暖时的误排；full_wide：全30架并将前瞻从8后继×5输入扩至16×12。

warm_rank按镜像、机器、架缓存版本和机器缓存版本记忆静态缺层量。FAIL清空机器缓存时同时递增元数据版本，避免新memo留住旧暖缓存；实际层拉取、真实收费、RUN/KILL、预算与资源对账逻辑保持原样。这里没有采用精确LRU报价，只改善静态预筛估价。

full_wide同步修改qr/qz/qm/qf矩阵、nq/sj数组、后继ns截断及输入k截断；仍在任何数组访问之前检查ns上限，外部输入与各前驱插入均受12列容量限制。

## 时间保险控制

保留原CPU保险，不能从总CPU低于1秒推断从未降级。另将基线/warm_rank的TS设为0，仅在fast00、standard00、large01三例对照：

| 程序 | 场景 | TS0与TS1完整报告相同 | TS0利润−TS1利润 |
| --- | --- | --- | ---: |
| baseline | fast_00 | True | +0 |
| baseline | standard_00 | True | +0 |
| baseline | large_01 | True | +0 |
| warm_rank | fast_00 | True | +0 |
| warm_rank | standard_00 | True | +0 |
| warm_rank | large_01 | False | -24,775 |

warm_rank在large01存在−24,775的差异，说明阶段CPU保险确实能在总CPU小于0.6秒时改变轨迹。该例是训练日志边界，不计范围内14例，但其余12个范围内场景没有做TS0对照；不能将所有利润差异都断言为纯放置策略收益。

## 定向回归

实际warm_rank源码通过17架构造：第17架只有机器缓存暖且架缓存冷时，可进入16架候选并一次RUN无仓库费；机器缓存按FAIL方式清空并递增版本后，旧暖估价正确失效，恢复原子预热且资源/配额/真实费用一致。
实际full_wide源码通过现有0/1/7/8/9/16/64/1000后继、20k指令预算与延后KILL生命周期回归。测试入口重命名原main会产生缺返回警告；三份实际候选生产编译均无警告。没有声称通过缺失的UBSan。
