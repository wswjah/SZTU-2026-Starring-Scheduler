# 星环算力平台调度（OJ 1846）——程序说明

## 题目与要求

深圳技术大学《数据结构》26 秋课程设计，OJ 题号 1846（比赛编号 2234），交互题。下面是按题面整理的摘要，不是原文；公式和数字与题面一致，完整题面以 OJ 页面为准。

### 任务

为算力平台"星环"写调度程序。平台由机房、机架、机器组成，租户不断提交由多个作业构成的工作流。评测程序扮演平台，按 tick 推进时间；每个 tick 它发来这一 tick 的事件和若干道抽查题（题面称"对账"），程序要回答对账题，并下达调度指令。

### 得分规则

共 100 组数据，得分 = 通过的组数。一组通过须同时满足：

1. 所有对账题回答正确；
2. 没有非法指令；
3. 利润不低于目标值 ⌈q·P\*⌉。

P\* 是出题方的调度程序在事先知道全部未来信息（每个作业的真实时长、每次故障的时刻）时的利润。q 在 0.10 到 1.09 之间，各组不同，与数据难易无关，约九成的组 q ≤ 1。P\*、q 和目标值都不公开。

### 平台模型

| 对象 | 要点 |
| :--- | :--- |
| 机房、机架、机器 | 机房有 CPU 单价 p_d；机架属于机房、接在一个网络节点上、有镜像缓存；机器在机架上，有 CPU 核数、内存、镜像缓存 |
| 网络 | 带权无向图，链路会断开和恢复，机房会停电（其节点不可经过）；dist(a,b) 是两个机架之间只经过正常节点和链路的最短路 |
| 租户与配额 | 租户构成一棵树，配额是 CPU 核数，按子树内运行中作业的 CPU 之和计；管理员会改配额（`QUOTA`），也会撤销（`UNDO k`，按栈恢复） |
| 镜像与缓存 | 镜像是一列层；每台机器、每个机架各有一个按层存放的 LRU 缓存，容量是各层大小之和 |
| 日志与告警 | 日志经赫夫曼编码后以十六进制发来；一行日志的告警分是所有模式串每次出现（允许重叠）的权重之和；机器的告警值是最近 W 个 tick 的告警分之和 |
| 工作流与作业 | 工作流有价值 v 和截止 tick；作业之间的依赖是有向无环图，全部作业完成工作流才算完成。作业有 CPU、内存、估计时长、镜像、外部输入、输出大小。**真实时长不公开**，与估计的偏差和租户有关，有时相差数倍 |

### 指令与合法性

每个 tick 回复 `ANS a_1 … a_nq`、若干行指令、`END`，每 tick 至多 20000 条指令，回复后要刷新输出。

| 指令 | 合法条件 |
| :--- | :--- |
| `RUN j x` | 作业待运行、前驱全部完成、工作流未被放弃；机器正常且空闲 CPU 和内存够；从所属租户到根的每个租户都不超配额；每份输入所在的机架都能到达机器所在的机架 |
| `KILL j` | 作业正在运行 |
| `DROP w` | 工作流已到达、未完成、未被放弃，且此刻没有正在运行的作业 |

非法指令不执行，出现一条该组就不通过。

### 启动、费用和收益

在 tick t 执行 `RUN j x`：

1. **传输数据**：每份不在本机架的输入，传输时间 = dist + ⌈z / B_net⌉，传输费 = z · dist · U_net；传输时间取各份的最大值。
2. **拉取镜像**：从底层到顶层逐层处理。在机器缓存里的不用拉；只在机架缓存里的算机架拉取量；两级都没有的算仓库拉取量，并放入机架缓存和机器缓存。拉取时间 = ⌈Q_reg / B_reg⌉ + ⌈Q_rack / B_rack⌉，拉取费 = Q_reg · U_reg。
3. **运行**：准备时间 S = max(传输时间, 拉取时间)，作业在 tick t + S + 真实时长 完成。

- 被终止或因机器故障中断的作业回到待运行状态，可以重新启动；已拉取的层留在缓存中，但故障机器的缓存会清空。
- 运行费 = c · p_d · (r − s)，s 是启动的 tick，r 是完成、被 `KILL` 或机器 `FAIL` 的 tick。已发生的费用一律不退。
- 工作流收益：在截止 tick dl 之前完成得 v；超过 dl 后在宽限期 G = max(5, ⌊(dl − 到达 tick) / 3⌋) 内线性衰减到 0；第 T 个 tick 结束时仍未完成的收益为 0。
- 利润 = 全部收益 − 全部费用。

### 事件和对账题

事件 11 种，按固定的类别顺序给出：`DONE`、`FAIL`、`UP`、`DCDOWN`、`DCUP`、`LDOWN`、`LUP`、`QUOTA`、`UNDO`、`LOG`、`WF`。

对账题 7 种，在本 tick 的全部事件处理之后、指令执行之前取值：

| 对账题 | 应回答 |
| :--- | :--- |
| `BILL o` | 租户 o 子树的累计费用（运行中的作业算到上一个 tick） |
| `HEAD o` | o 到根路径上各租户"配额 − 已用"的最小值 |
| `ROUTE a b` | 机架 a、b 的最短路，不可达为 −1 |
| `ALARM x` | 机器 x 的告警值 |
| `SLACK j` | 作业 j 在所属工作流未完成作业构成的图上的松弛时间（用估计时长） |
| `CACHE x` / `RCACHE r` | 机器 / 机架缓存中各层大小之和 |

## 我是怎么分析题目的

这一节是 2026-11-14 事后整理的。v1 读题时的原始思考过程已经随上下文压缩丢失，这里依据的是题面、代码和两份开发记录，按"从题面读出了什么、因此怎么做"来写。

**1. 三个通过条件的性质不同，决定了做事的顺序。** 对账和合法性是硬门槛，错一处该组就是 0；利润是连续量，高一点就可能多过一组。所以先把对账和合法性做到全对，再做利润。7 类对账题都能按规则确定地算出来，没有需要猜的地方，这一部分可以用本地评测程序逐类验证到零错误。

**2. 每类对账题对应一种需要增量维护的状态。** 对账题每组最多 3500 道，但事件很多，每次查询时重算不划算。

| 对账题 | 维护的状态 |
| :--- | :--- |
| `BILL` | 每个租户的费用拆成"固定部分 + 费率 × 时间"，沿租户树汇总 |
| `HEAD` | 每个租户的配额和已用量；配额修改带撤销栈 |
| `ROUTE` | 机架两两之间的最短路；链路或机房事件后只重算受影响的源机架 |
| `ALARM` | 赫夫曼解码 + AC 自动机求每行的告警分，按 W 个 tick 的窗口滑动 |
| `SLACK` | 工作流未完成作业构成的图上的最长路 |
| `CACHE` / `RCACHE` | 严格按题面的顺序模拟两级 LRU 缓存 |

题面里有几处取值时刻和顺序容易错：对账题在事件之后、指令之前取值；`BILL` 的运行费只算到上一个 tick；`SLACK` 只看未完成的作业；LRU 的"移到最近使用端"和"放入后再淘汰"的先后顺序。

**3. 收益按工作流结算，费用按作业发生，所以决策单位是工作流。** 一条工作流全部作业完成才有收益，而每个作业一启动就产生不退的费用。做了一半没做完的工作流是净亏。由此得到程序的主线：每条工作流估计剩余关键路径和剩余成本，期望收益高于剩余成本才开工，开工后一旦不再划算就 `KILL` 止损。收益在截止时间之后线性衰减，所以完成时间用 5 个情景来算期望，而不是只用一个预测值。

**4. 真实时长不公开，但题面说偏差"和租户有关"。** 这句话说明偏差可以学：用已完成的作业、以及已经超过估计时长仍在跑的作业，按租户估计"真实 / 估计"的比值。练习场景的参数文件里有 `bias_lo 0.7`、`bias_hi 1.8`、`straggler_p 0.08`，也印证了偏差按租户设定、并有少数特别慢的作业。

**5. 三种费用可以折算成同一个代价，用来选机器。** 运行费从启动的 tick 算起，所以准备时间（传输和拉取）既推迟完成、又要付运行费；传输费正比于数据量 × 距离，鼓励把作业放在前驱输出所在的机架；拉取费只在从仓库拉取时发生，鼓励复用缓存。选机时先按"传输费 + 延迟代价 + 运行费"给机架排序，再在最好的几个机架里逐台机器比较。

**6. 故障有前兆，但没用上。** 参数文件里有 `precursor_frac 0.65`、`falsealarm_frac 0.1`，说明日志告警是故障的前兆。v1 分析过告警与故障的关系并试了规避，故障浪费降了 4–6%，总利润没有提升，没有采用。

**7. 目标值不公开，只能找一个外部标尺。** q 与难易无关、约九成不超过 1，所以没有理由针对某类数据，只能追求整体利润。P\* 未知，我用一份公开的、自述 OJ 得 81 分的程序当利润标尺，只比较利润数字。当时推测"利润每高 1% 约多过 1 组"，这个推测后来被证明不准：v2 本地利润高 23.6%，OJ 只多过 7 组。

**8. 规模和时间限制决定了实现方式。** 6 万个作业、600 个 tick、360 台机器、1 秒，每个 tick 的调度不能对所有作业和机器做全量枚举。所以工作流的重估加了脏标记，候选机架只取前几个，并加了按 CPU 时间逐级降级的保险。源码限制 16384 字节，而开发版有三十多 KB，需要压缩脚本。

**9. 题面说本地评测程序"与正式评测按同一套规则运行"，并能按参数文件生成同等规模的场景。** 所以先搭本地评测环境，用随机生成的场景做对比，而不是靠提交来试。提交机会只有 10 次，这也是唯一可行的做法。

**10. v2 重读规则时才注意到的两处。**

- 启动规则说层在执行 `RUN` 时就放入缓存，被终止的作业"已拉取的层留在缓存中"，运行费按 (r − s) 计。三条合起来：同一个 tick 内 `RUN`、`KILL`、再 `RUN`，第一次启动的运行费为 0，第二次启动不用再等拉取。v1 读题时没有把这三条放在一起看。这是利用规则，不是常规调度手段。
- "第 T 个 tick 结束时未完成收益为 0"这一条，v1 实现成了"预计完成时间超过 T 就整条放弃"。预计值本身有误差，这样会误杀只差一点的工作流。v2 改为按情景分别判断并留容差。

**11. 仍然没弄清的。** OJ 上还有 4 组没通过，原因不明。题面说 q 最高到 1.09，即有的组要求利润高于出题方已知全部未来信息时的结果；这些组是否就是没通过的那几组，我不知道。

**v2 走过的弯路**：三轮参数扫描的变化都在 ±1% 左右，没有采用；压缩脚本把标准库名字改名导致编译失败；采样时采错进程、采样拖慢程序触发超时保险，得到过利润掉 19% 的假结果；issue 留言里两处数字写错后更正；CPU 优化只做到 v1 的 1.2 倍，没达到验收标准。

三处改动：

1. **同一 tick 内 `RUN` → `KILL` → `RUN`**（+17.5%）。题面规定镜像层在 `RUN` 时就进缓存，被终止的作业"已拉取的层留在缓存中"，运行费按 c·p·(r−s) 计。所以先启动、立刻终止、再启动，第二次启动的拉取时间为 0，第一次的运行费也为 0。官方本地评测程序判为合法。**这是利用规则，不是常规调度手段**；不想用时交 `submit_nowarm.cpp`。
2. **终点的处理**（+4.3%）。原来预计完成时间一超过 T 就整条放弃，改为按 5 个完工时间情景分别判断并留 30 tick 的容差；排队延迟不再计入完工时间预测。
3. **机架排序计入仓库拉取费**，候选机架从 6 个增加到 12 个（合计约 +0.9%，接近噪声）。

没达到的一项：v2 的 CPU 用时比 v1 高约 20%–25%（开工的工作流更多）。按 v1 在 OJ 的 444 ms 推算约 530–560 ms；v2 的成绩截图里用时一列没有显示数字，这个推算仍没有得到验证。

## 算法概要

1. **对账**：7 类问题对应的状态全部增量维护——租户账单（固定部分 + 费率 × 时间，沿租户树汇总）、
   配额余量（带撤销栈）、机架间最短路（链路事件只重算受影响的源机架）、机器/机架的 LRU 镜像层缓存、
   告警得分（哈夫曼解码 + AC 自动机）、作业在工作流 DAG 中的松弛量。
2. **时长估计**：作业真实时长不公开且与租户有关，用已完成作业和"已经超期仍在跑"的作业
   按租户学习 真实/估计 比例，并向全局比例收缩。
3. **工作流取舍**：估计剩余关键路径（含准备、排队时间）和剩余成本，按 5 个完工时间情景求期望收益；
   期望收益高于剩余成本才开工，开工后一旦不再划算就 `KILL` 止损。
   调度顺序按"单位核时期望利润"，已开工的、时间紧的优先。
4. **选机**：先按 传输费 + 延迟代价 + 运行费 给机架排序，并向前看一步
   （后继作业将来汇集输入要付的代价）；在最好的几个机架里逐台机器计价（镜像拉取、等待时间）。
   每台机器维护一条预计释放时间线，允许作业"预约"一台正忙但更合适的机器。
5. **超时保险**：按 `clock()` 监控 CPU 时间，落后于预算时逐级降级（先停周期性重估，再隔 tick 调度）。
6. **v2 新增**：同 tick 预热缓存；按情景判断是否来得及在 T 之前完成；机架排序计入仓库拉取费。
